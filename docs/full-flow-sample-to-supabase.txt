FULL FLOW: SAMPLE DELIVERY UNTIL SUPABASE
Date: 2026-11-13

Architecture:

Load cell
  -> HX711
  -> ESP32
  -> MQTT broker
  -> Backend MQTT consumer
  -> Supabase PostgreSQL
  -> Native mobile app

The backend receives the full raw sample stream. It performs filtering, stable-window detection, quality evaluation, and final-weight creation.

============================================================
1. ESP32 READS THE LOAD CELL
============================================================

Hardware flow:

Load cell -> HX711 -> ESP32

The ESP32 reads weight repeatedly. Example:

sample 1: 12.00 kg
sample 2: 12.20 kg
sample 3: 12.10 kg
sample 4: 12.15 kg

Each sample needs:

- device_id
- session_id
- sample_number
- recorded_at
- raw_weight_kg
- message_id

The ESP32 does not write directly to Supabase. It publishes samples to MQTT.

============================================================
2. CREATE WEIGHING SESSION
============================================================

A weighing session represents one weighing attempt.

Example:

session_id = session-001
device_id  = scale-001
animal_id  = goat-001

The backend creates a row in weighing_sessions:

status = collecting
sample_count = 0

Main weighing_sessions columns:

- session_id
- device_id
- animal_id
- started_at
- ended_at
- status
- sample_count
- finalized_at
- finalized_weight_kg
- finalization_algorithm_version
- finalization_threshold_version
- rejection_reason
- created_at
- updated_at

Valid status values:

collecting | processing | accepted | rejected | timeout

============================================================
3. ESP32 PUBLISHES SAMPLE TO MQTT
============================================================

Example MQTT topic:

livestock/scale/scale-001/session/session-001/samples

Example payload:

{
  "message_id": "msg-000001",
  "device_id": "scale-001",
  "session_id": "session-001",
  "animal_id": "goat-001",
  "sample_number": 1,
  "recorded_at": "2026-11-12T10:00:00.000Z",
  "raw_weight_kg": 12.00
}

MQTT broker responsibilities:

- receive messages;
- authenticate the device;
- route messages to the backend consumer;
- apply MQTT QoS behavior;
- retry delivery according to configuration.

MQTT broker is transport, not permanent storage.

============================================================
4. BACKEND RECEIVES AND VALIDATES MESSAGE
============================================================

The backend subscribes to the MQTT topic and checks:

- device_id is registered;
- session_id exists and is active;
- sample_number is valid;
- recorded_at is valid;
- raw_weight_kg is valid;
- message_id has not already been processed.

The backend uses session_id and sample_number for idempotency.

Database constraint:

UNIQUE (session_id, sample_number)

Therefore:

session-001 + sample 1 -> accepted
session-001 + sample 1 -> duplicate; not inserted again

============================================================
5. SAVE SAMPLE TO weighing_samples
============================================================

The backend inserts the raw sample:

INSERT INTO weighing_samples (
    session_id,
    recorded_at,
    raw_weight_kg,
    filtered_weight_kg,
    sample_number
)
VALUES (
    'session-001',
    '2026-11-12T10:00:00.000Z',
    12.00,
    NULL,
    1
);

weighing_samples stores:

- sample_id: internal sample ID;
- session_id: parent weighing attempt;
- recorded_at: time generated by ESP32;
- raw_weight_kg: original load-cell value;
- filtered_weight_kg: filtered value, added later;
- sample_number: source order number.

Relationship:

weighing_sessions 1 -> many weighing_samples

The backend updates the session count:

UPDATE weighing_sessions
SET sample_count = sample_count + 1,
    updated_at = NOW()
WHERE session_id = 'session-001';

sample_count is a summary count. Actual sample data remains in weighing_samples.

============================================================
6. ORDER SAMPLES
============================================================

MQTT messages can arrive out of order:

received: sample 1, sample 3, sample 2, sample 4

The backend sorts using:

- sample_number; or
- recorded_at from ESP32.

The backend must not use MQTT arrival time as measurement time.

============================================================
7. CHANGE SESSION TO processing
============================================================

When enough samples arrive:

UPDATE weighing_sessions
SET status = 'processing',
    updated_at = NOW()
WHERE session_id = 'session-001';

The backend reads samples in order:

SELECT
    sample_number,
    recorded_at,
    raw_weight_kg
FROM weighing_samples
WHERE session_id = 'session-001'
ORDER BY sample_number ASC;

============================================================
8. FILTER SAMPLES
============================================================

The backend applies the selected filter. Example:

raw sample     filtered sample
12.00          12.00
15.30          12.66
 9.80          12.09
14.20          12.51
12.60          12.53
12.40          12.50
12.50          12.50
12.45          12.49
12.50          12.50
12.48          12.49

The backend updates filtered_weight_kg. Raw values remain unchanged.

============================================================
9. FIND STABLE WINDOW
============================================================

The backend applies a sliding window to the samples.

Example selected window:

[12.53, 12.50, 12.50, 12.49, 12.50]

The backend calculates:

- window duration;
- sample count;
- median;
- mean;
- variance;
- standard deviation;
- minimum weight;
- maximum weight.

Example result:

window_duration_ms = 250
sample_count       = 5
window_median_kg   = 12.50
window_mean_kg     = 12.504
window_variance    = 0.002
window_stddev_kg   = 0.045
min_weight_kg      = 12.49
max_weight_kg      = 12.53

The backend checks rules such as:

- variance below threshold;
- minimum duration reached;
- minimum sample count reached;
- weight below scale capacity;
- plausible weight change;
- no excessive missing samples.

Threshold values are not final until validated with real goat data and a reference scale. Testing must balance false acceptance and false rejection.

============================================================
10. SAVE WINDOW QUALITY DATA
============================================================

The selected window's summary is saved in weighing_quality.

INSERT INTO weighing_quality (
    session_id,
    window_duration_ms,
    sample_count,
    window_median_kg,
    window_mean_kg,
    window_variance,
    window_stddev_kg,
    min_weight_kg,
    max_weight_kg,
    algorithm_version
)
VALUES (
    'session-001',
    250,
    5,
    12.50,
    12.504,
    0.002,
    0.045,
    12.49,
    12.53,
    'v1.0'
);

weighing_quality stores calculated window statistics. All individual samples remain in weighing_samples.

Current schema stores window summary, not explicit window membership. If exact reproduction is needed, add:

- window_start_sample;
- window_end_sample;
- window_start_at;
- window_end_at.

weighing_quality has a unique session_id, so one session has at most one quality summary.

============================================================
11. ACCEPTED RESULT: SAVE weighings
============================================================

If stable-window rules pass:

final_weight = 12.50 kg
stable_weight_detected = true
quality_status = accepted

The backend inserts the finalized result:

INSERT INTO weighings (
    session_id,
    animal_id,
    device_id,
    measured_at,
    weight_kg,
    measurement_source,
    measurement_method,
    stable_weight_detected,
    quality_score,
    quality_status
)
VALUES (
    'session-001',
    'animal-001',
    'device-001',
    '2026-11-12T10:00:00.250Z',
    12.50,
    'iot',
    'stationary',
    TRUE,
    0.98,
    'accepted'
);

weighings stores the accepted final measurement:

- weighing_id;
- session_id;
- animal_id;
- device_id;
- measured_at;
- weight_kg;
- measurement_source;
- measurement_method;
- stable_weight_detected;
- quality_score;
- quality_status.

The database now enforces:

weighing_session 1 -> zero-or-one weighing

weighings.session_id is UNIQUE. One session cannot create two finalized weighings.

============================================================
12. UPDATE SESSION TO accepted
============================================================

After final records succeed:

UPDATE weighing_sessions
SET status = 'accepted',
    ended_at = NOW(),
    finalized_at = NOW(),
    finalized_weight_kg = 12.50,
    finalization_algorithm_version = 'v1.0',
    finalization_threshold_version = 'threshold-v1',
    updated_at = NOW()
WHERE session_id = 'session-001';

============================================================
13. FAILED SESSION
============================================================

A failed session is still saved. It is not deleted.

Example failure:

session_id       = session-002
status           = rejected
sample_count     = 35
rejection_reason = variance_above_threshold

The samples remain in weighing_samples for audit and research. Quality data can remain in weighing_quality with rejection_reason.

No row is created in weighings because no valid final weight exists.

Flow:

session-002
  -> samples collected
  -> stable-window test fails
  -> status = rejected
  -> no finalized weighing

Other failure reasons:

- variance_above_threshold;
- insufficient_samples;
- duration_too_short;
- overload;
- missing_samples;
- timeout;
- implausible_weight_change.

The farmer can start another attempt:

session-002 -> rejected
session-003 -> accepted -> weighing-001

The new attempt receives a new session_id. One weighing must not contain many sessions.

============================================================
14. TRANSACTION IN SUPABASE
============================================================

Accepted finalization should use one database transaction:

BEGIN;

INSERT INTO weighing_quality (...);
INSERT INTO weighings (...);
UPDATE weighing_sessions
SET status = 'accepted',
    finalized_at = NOW(),
    finalized_weight_kg = 12.50
WHERE session_id = 'session-001';

COMMIT;

If any operation fails:

ROLLBACK;

This prevents incomplete final data, such as an accepted session without a final weighing.

============================================================
15. SUPABASE TABLES USED
============================================================

Primary tables:

1. weighing_sessions
   One weighing attempt and processing state.

2. weighing_samples
   Every raw and filtered sample from MQTT.

3. weighing_quality
   Stable-window statistics and rejection reason.

4. weighings
   Accepted final weight only.

Supporting tables:

5. devices
   ESP32 or IoT scale identity.

6. animals
   Animal identity.

7. audit_logs
   Data-change audit trail.

8. sync_operations
   Client-side mobile sync log. Not the main MQTT ingestion path.

Relationships:

animal 1 -> many weighing_sessions
weighing_session 1 -> many weighing_samples
weighing_session 1 -> zero-or-one weighing
weighing_session 1 -> zero-or-one weighing_quality

============================================================
16. MOBILE APP RESULT
============================================================

The mobile app reads the processed result through Supabase API or realtime channel.

Example displayed result:

Status: Accepted
Animal: Goat-001
Final weight: 12.50 kg
Quality score: 0.98
Measurement time: 2026-11-12 10:00:00

The mobile app does not need to calculate the final IoT weight. It can read raw samples and quality data for audit or charts.

============================================================
COMPLETE FLOW
============================================================

1. ESP32 reads load-cell value.
2. ESP32 identifies device and weighing session.
3. ESP32 publishes timestamped raw sample to MQTT.
4. MQTT broker routes message to backend consumer.
5. Backend validates message and prevents duplicates.
6. Backend inserts sample into weighing_samples.
7. Backend updates weighing_sessions.sample_count.
8. Backend orders samples by sample_number or source timestamp.
9. Backend applies filtering.
10. Backend changes session status to processing.
11. Backend searches for stable window.
12. Backend calculates median and quality statistics.
13. Backend saves window summary to weighing_quality.
14. If accepted, backend inserts final result into weighings.
15. Backend changes session status to accepted.
16. Supabase transaction commits.
17. Mobile app reads finalized result.
18. If processing fails, session becomes rejected or timeout and no weighing row is created.

Important limitation:

If internet fails before MQTT receives the message, the sample may not reach Supabase. Offline operation requires ESP32 local flash buffering and replay, or a local gateway that stores and forwards messages later.
